# Windows desktop preview

The Windows host shares Sahib's existing HTML/CSS/JavaScript application. Tauri owns the tray, windows, startup registration, notifications, scheduling and audio output. Android remains planned.

## Build

Install Node.js 22+, current stable Rust with the MSVC target, Microsoft C++ Build Tools with the Windows SDK, and WebView2. Then run `npm ci`, `npm run desktop:test`, `npm run desktop:acceptance`, and `npm run desktop:build`. Run `npm run desktop:checksum` to generate the current installer's SHA-256 file. The per-user NSIS installer is written to `src-tauri/target/release/bundle/nsis/`. An unsigned preview installer may require Windows confirmation. Production signing and automatic updates are not configured.

`npm run desktop:dev` runs a local desktop build. `tools/prepare-desktop.mjs` copies an explicit runtime allowlist into `dist/`; it excludes private imports, reports and tests. The browser website has no new build requirement. Only the packaged entry loads `js/desktop.js` and skips browser service-worker registration.

## Scheduling contract

The shared JavaScript prayer provider generates the timetable. API timetables carry their IANA timezone; offline Adhan.js timetables retain the device timezone they use. The shared date converter resolves wall-clock times into UTC milliseconds using the date's DST offset. Rust never calculates a second prayer timetable.

The adapter exports 35 days of prayer moments and enabled alerts. Each alert has a stable identity, UTC time, title/body, sound selection, volume and notification flag. A replacement cancels obsolete events. The native host persists the schedule and a fired-event ledger, prevents multiple app instances, and checks deadlines independently of WebView timers. Practice occurrences/completion/quiet-hours rules come from the existing daybook. Prayer preference or practice changes invalidate pending native alerts before rebuilding the schedule.

The schedule refreshes on setting changes and every six hours while running. The native host also detects Windows timezone/DST changes and large wall-clock jumps, invalidates pending alerts, and asks the shared provider to rebuild. Offline month caches are reused only when their saved device timezone still matches. Religious calculation rules are unchanged. Saved future events survive an app restart. Alerts older than two minutes do not replay after sleep; if several are due on resume, only the latest may sound. The scheduler does not wake a sleeping PC. Quitting Sahib stops reminders. The cached schedule has a finite horizon; open the app to refresh it if the widget reports expiry. Native scheduling stays active when the main window is hidden in the tray.

## Window and widget

Settings → Windows offers close-to-tray, optional startup, start minimized, widget visibility, always-on-top, opacity and click-through. Drag the widget header to move it; its position is saved. The tray menu can restore widget clicks, stop audio, reopen Sahib or quit. One shared schedule supplies the window, widget and tray tooltip. The widget follows the app's language, palette and font.

In preview 0.2.2, Windows settings groups visibility and placement, appearance, startup/background behavior, and advanced interaction. Choose **Taskbar overlay** to show a compact next-prayer clock and countdown on the taskbar. Clicking it opens today's six timetable markers (including sunrise), Gregorian/Hijri dates, daily practice items and tomorrow's fasting prompts. Escape, the close button, or clicking another window collapses the taskbar panel. Open Sahib, Full timetable and Settings actions sit along the bottom; refresh and active-audio stop controls remain available. The floating card remains available.

Appearance can follow the Windows taskbar's light/dark colours, follow the current Sahib palette/font, or independently select Sahib, Aura, Dracula, Catppuccin, Rosé Pine or Tokyo Night. The independent families follow Sahib's light/dark mode. The panel and prayer cards use opaque surfaces to prevent background text bleeding through. The saved opacity setting controls frame opacity; text and controls stay opaque. The panel height follows its content, capped by the selected monitor work area, with scrolling when needed. A configurable lead window highlights a prayer that is approaching without flashing.

Select one display or **All taskbar displays**. Each compact widget can be dragged horizontally; manual positions are saved separately for each display. The right preset stops before the detected notification area (or a conservative reserved area when detection is unavailable). Left/right spacing can be adjusted independently. It is an independent window placed over the horizontal taskbar, not an Explorer toolbar and not code loaded into Explorer. It does not reserve taskbar space. Native window events trigger a coalesced geometry/visibility audit, with a ten-second safety audit for missed events. Actual taskbar coverage or loss of topmost status triggers a non-activating order repair; unchanged audits do not repeatedly force topmost. Ordinary maximized windows leave it visible; fullscreen client coverage, including maximized borderless windows, temporarily hides it. If there is insufficient usable taskbar width, the widget falls back to a floating card. Side taskbars, unusual shell replacements and taskbar crowding may need the floating mode or manual adjustment. See the [Awqat Salaat comparison and native-host evaluation](WINDOWS-WIDGET-HOSTING.md).

The compact and expanded widgets currently use WebView2, and hiding the main window keeps its WebView loaded. Seeing WebView2 processes with only the taskbar widget visible is expected in this preview. Native scheduling/audio runs in Rust, but that does not remove the UI runtime. A native compact host plus unloading/recreating hidden web interfaces would be needed to eliminate this runtime while only the compact widget is displayed.

Visibility diagnostics are stored beside `desktop-state.json` in the application's data directory: `widget-diagnostics.jsonl`, plus one rotated previous file, each approximately capped at 2 MiB. `desktop_state` exposes the resolved `widgetLogPath`. Entries record actual bounds, visibility, cloaking, stacking observations, foreground class, monitor/taskbar geometry, and intentional hide reasons. They exclude window titles and prayer text. Taskbar rank is recorded when the center-point hit test finds the taskbar covering the widget; otherwise it is -1. This is diagnostic evidence, not proof that every pixel is unobscured.

The daily items reuse the existing practice occurrence, completion, snooze and exclusion rules. Tomorrow's optional fasting prompts reuse the calendar's Monday/Thursday, white-days and seasonal fast definitions, including the existing Eid/Tashriq exclusions. They are informational; enabling widget prompts does not enable OS notifications or subscribe the user to a new practice. Turn on practice notifications in Practice settings and prayer alerts in Alerts separately. Hijri dates follow Sahib's existing Umm al-Qura calendar.

## Storage and audio

The desktop WebView has its own profile, separate from the browser/PWA. Existing JavaScript APIs, IndexedDB database/store names and application data formats remain unchanged. Browser data is not automatically copied. Existing export/import tools transfer the data they support; locally imported PDFs/audio and other preferences may need separate re-import/configuration.

Native host settings, schedules and its fired-event ledger live under the app's local data directory (`com.sahib.companion`). Imported adhan audio is validated and copied into that private directory for playback while the window is hidden. Bundled recordings retain the notices in `assets/adhan/LICENSES.md`; this native build grants no additional recording rights. The native mixer opens only for playback and closes when idle. Stop is available in the app, widget and tray.

Only local application windows can use the bridge. Main-only commands reject calls from the widget. Audio selections use fixed identifiers and private slots; paths from the UI cannot read arbitrary files. External HTTP(S) links open through the OS. Remote top-level navigation inside the privileged WebView is blocked. No general filesystem or shell API is exposed to the UI.

The shared interface currently uses inline event attributes for navigation and generated controls. The desktop CSP explicitly permits these with `script-src-attr`; script elements still use Tauri's generated hashes/nonces. Without the separate attribute directive, those hashes cause browsers to ignore `unsafe-inline` in `script-src`, blocking button clicks. `tests/desktop-navigation.js` exercises actual button handlers to catch this regression.

## Verification limits

Rust tests cover schedule validation, restart deduplication, missed-event suppression, cancellation, and decoding without opening an audio device. Real WebView checks must additionally cover startup, language/theme, prayer settings, PDFs, native playback/stop, hiding/reopening, widget preferences and restart persistence. OS notification visibility depends on Windows notification settings and Focus Assist. Autostart changes the current user's Windows startup registration only when explicitly enabled in Settings.

The native scheduler now checks at most one second apart, so a schedule added while the loop was idle does not wait up to 30 seconds. Silent practice notices cannot suppress an adhan due at the same deadline. The local `--media` acceptance suite schedules both the standard and Fajr recordings against real native deadlines at zero volume, verifies native output streams, and exercises the widget's stop button. It also checks calendar examples, all palette families, RTL, physical taskbar placement when Explorer is available, and compact/panel interactions. These checks do not measure speaker loudness, prove notification banners are visible under every Windows policy, or wake a sleeping/closed PC.

`npm run desktop:acceptance` builds a packaged debug app with the separate identity `com.sahib.companion.qa` and a fresh private profile under `.qa/`. It checks actual navigation clicks, settings, timezone conversion, PDFs, reminder cancellation, chime-only reminders without imported audio, widget permissions, close-to-tray, a silent native event while hidden, and restart persistence. Reports and screenshots are saved alongside the profile. Add `-- --media` to check imported audio and PDF playback on a Windows machine with an audio output device. The online PDF checks need network access.

The Windows preview workflow repeats the resource, Rust, and packaged acceptance checks before building an unsigned installer. It uploads the installer, checksum, and test evidence as GitHub Actions artifacts for 14 days. Private test profiles are excluded. It does not publish a release or change the website deployment. Hardware audio tests remain a local check because hosted runners may have no sound device.

The browser expressions in `tests/desktop-*.js` must only run against disposable profiles. Debug builds accept `SAHIB_TEST_DATA_DIR` to isolate both the host state and WebView profile; release builds ignore that override. With that test profile set, debug builds also accept `SAHIB_TEST_CDP_PORT` and pass it directly to WebView2, including on elevated CI runners where WebView2 ignores environment overrides. Release builds contain no test-port override. The acceptance runner uses a temporary local port only for its own QA process and closes that process afterward. Do not enable remote debugging for ordinary use.

## Preview 0.2.3 verification

See [the 0.2.3 memory and verification report](WINDOWS-0.2.3-VERIFICATION.md) for the three-configuration comparison, actual native captures and remaining hardware/accessibility limits. The ordinary installer keeps the web widget. Native compact mode and main-window unloading require an intentional [experimental feature build](WINDOWS-MEMORY-ARCHITECTURE.md); they are not the default.

Settings → Alerts now explicitly states when prayer alerts are off. **Enable Adhan for all five prayers** enables at-time playback while preserving volume and recordings. Enable notifications separately if wanted. Selecting a timing option alone does not enable alerts. Personal settings are never silently enabled by this update.

See [the verification report](WINDOWS-0.2.2-VERIFICATION.md) for real monitor checks, screenshots, idle measurements, and unexecuted hardware scenarios. `npm run desktop:acceptance -- --media --windows --reliability --soak-minutes=10` adds local audio checks, controlled WinForms obstruction windows, and actual Explorer taskbar promotions to reproduce and test stacking recovery. It temporarily tests taskbar auto-hide and restores its original state and cursor position in a finally block. Use an interactive Windows session; CI runs the ordinary packaged suite without these display experiments. `-- --measure` records a short isolated process-tree idle sample; `--skip-build` reuses the QA executable and still verifies its separate identity. The historical [0.2.1 report](WINDOWS-0.2.1-VERIFICATION.md) remains available.
